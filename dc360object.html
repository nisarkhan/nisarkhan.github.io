Data 360 Objects: DSO, DLO & DMO

Salesforce Data 360 (formerly Data Cloud) has three kinds of object, and your data moves through them in order - ingested, refined, then harmonized. Here is what each one is in plain terms, plus a cooking analogy that makes it stick.

// start here

The three objects, at a glance

Every source you bring into Data 360 produces the same chain of objects. Two of them are created for you automatically; the third is where you do the real work.

Data Source Object DSO

The data exactly as it is in the source system.

If the source file has 10 columns with certain headers, the DSO has the same 10 columns and the same headers. Original format (e.g. CSV), or transient storage for built-in connectors like Marketing Cloud.

Data Lake Object DLO

Created automatically alongside the DSO, with the same name.

Holds the same raw data, but this is where you can enrich it - add transformations and formula fields - and it carries system-generated fields like source IDs.

Data Model Object DMO

Where harmonization happens.

You map DLO data into a standard structure so it is consistent and connected across every source - ready for insights, segmentation and activation.

Source → DSO → DLO → DMO → insights · segments · activation
// object 1
Data Source Object

DSO - the data as-is

The DSO is where the data lands in its as-is form, straight from the source system. Nothing is changed. If your source file has 10 columns, the DSO has 10 columns, with the exact same headers the source uses.

Whenever you ingest data into Data 360 and you want it untouched - a faithful copy of what came in - that is the DSO. It is the original file format (for a file upload, that is the CSV itself), or transient storage in the case of built-in connectors such as Marketing Cloud.

Rule of thumb

DSO = a mirror of the source. Same columns, same names, no logic applied.

// object 2
Data Lake Object

DLO - raw data, plus a little refinement

You do not create the DLO yourself. When a data stream is created and the DSO becomes available, Salesforce automatically creates a matching DLO with the same name.

The DLO still contains the raw data, but it is the layer where that data can be made more useful:

  • Transformations - apply logic to clean or reshape the incoming data.
  • Formula fields - derive new values from the fields you already have.
  • System-generated fields - things like source IDs that Data 360 adds for you.

So both the DSO and the DLO are created during ingestion. The difference: the DSO is only ever the as-is data, while the DLO has the as-is data plus whatever enrichment and refinement you add on top.

// object 3
Data Model Object

DMO - harmonized and ready for the business

The DMO is where the real magic happens: harmonization. You take the data from a DLO and map it onto a standard structure that Salesforce provides.

Why bother? Because mapping many different sources onto one shared model gives you consistent, connected data that is ready for business use. The DMO layer is what the rest of Data 360 runs on - insights, segmentation, activation, and the algorithms Salesforce ships all read from DMOs.

Salesforce provides a large catalog of DMOs as a ready-made data model, so you are usually mapping into existing DMOs rather than inventing your own.

// the one that sticks

Picture cooking a meal.

Everything cooked, combined and plated. Ready to serve.

The one mapping rule

Mapping is always done in one direction, between one pair of objects:

Always

DLO → DMO

You never map DSO → DMO. You never map DLO → DLO. Mapping goes from a DLO to a DMO, every time. That is how the standard model stays consistent no matter how many sources feed into it.

// the catalog

Frequently used DMOs

Salesforce ships many DMOs. These are not the only ones, and the others matter too - but most real-world use cases lean on a small set:

DMO What it represents
Individual A person or customer - first name, last name, date of birth, and privacy preferences. One of the most important objects in the model.
Case Support tickets, brought in together with their associated account and user.
Contact Point How to reach someone - the communication details (email, phone, and so on) held in Data 360.

Which DMO fits depends on your use case, so start from the question you are trying to answer and work back to the object.

Subject areas

Every DMO in Data 360 is logically grouped under a subject area. A subject area is just a way of keeping the data model organized and easy to navigate - related objects sit together instead of being scattered across one long list.

So in a given data model, the subject area is the name of the group, and the entities listed under it are the DMOs that belong to that group.

// the one you'll use most

The Party subject area

The Party subject area is a collection of DMOs that represent contact-related information. The objects grouped under it include:

Party Account Individual Contact Point Address …and more

When you bring data in from multiple sources and want to build a unified picture of a customer or an account, you map it to the DMOs under Party. It pulls all the information about a person or an organisation into one place.

In simple terms: Party is your go-to layer for managing and retrieving contact information in a unified way.

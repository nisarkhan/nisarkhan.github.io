Semantic Search Implementation Guide

The complete, verified path from an empty Data Cloud to a working Agentforce agent that finds similar Cases and RFI Questions by meaning, not keyword. Every command, field name, and code sample here was tested end-to-end against a live org.

Audience: an engineer setting this up for the first time Agent: RFI_Case_Analysis_Agent_Script Status: live & tested Repo: github.com/nisarkhan/amazon-fintech Also see: the original planning PDF (kept locally, not linked here)

Architecture at a glance

Agentforce Agent (Agent Script) "RFI_Case_Analysis_Agent_Script" - 2 actions │ ├── get_case_summary ──► apex://GetCaseSummaryFields (pure SOQL, no Data Cloud) │ │ │ └─► CaseSummaryResponse (CLT) ──► caseSummaryCard (LWC) │ └── find_similar ──► apex://FindSimilarCases (Data Cloud vector search │ + SOQL/SOSL fallback) └─► SimilarCasesResponse (CLT) ──► similarCasesCard (LWC) FindSimilarRfiQuestions - same pattern as FindSimilarCases, but NOT yet wired to an agent action (see §3.4) Data Cloud: Case_Home ──► ssot__Case__dlm ──► Case_index__dlm / Case_chunk__dlm RFI_Question__c_Home ──► RFI_Question_c_Home__dlm ──► RFI_Question_c_Home_index__dlm / _chunk__dlm

Three Apex classes matter here:

Class Uses Data Cloud? Wired to agent action?
GetCaseSummaryFields No - pure SOQL (record Id, Case Number, keyword phrase, SOSL) ✓ get_case_summary
FindSimilarCases Yes - vector search, primary path ✓ find_similar
FindSimilarRfiQuestions Yes - vector search, primary path not wired

GetCaseSummaryFields was deliberately not migrated to Data Cloud - it does exact lookups (by Id, by Case Number, or an exact-phrase match), which SOQL already does instantly. Semantic search earns its cost on the fuzzy "find similar" use case, not on "look up this specific case."

Data Cloud setup

1.1 Prerequisites

  • Data Cloud provisioned and enabled on the org
  • Salesforce CRM Connector active: Setup → Data Cloud → Salesforce CRM
  • Case and RFI_Question__c objects already have data in the org

1.2 Create two CRM Data Streams

Setup → Data Cloud → Data Streams → New → Connected Source: Salesforce CRM

Object Stream name Category Key fields
Case Case_Home Other Id (PK), CaseNumber, Subject, Description, Status, Priority, Origin, CreatedDate, ClosedDate
RFI_Question__c RFI_Question__c_Home Other Id (PK), Name, Question_Text__c, Response_Text__c, Category__c, Status__c, Priority__c, Due_Date__c, Requesting_Institution__c, Case__c (FK)

Click Deploy on each, then wait for ImportRunStatus = SUCCESS. Don't trust the TotalRowsProcessed column - check TotalNumberOfRowsAdded instead; the former is frequently 0 even on a healthy stream.

⚠ Case__c is the field that makes cross-object matching possible

If you skip mapping Case__c, "find similar cases via RFI questions" (§2.1) degrades to Case-text-only matching.

1.3 Map each stream to a Data Model Object (DMO)

Data Streams → (stream) → Data Mapping → Start

  • Case_Home → auto-maps to the standard ssot__Case__dlm. Only carries the fields you mapped - ours has ssot__Id__c, ssot__CaseNumber__c, ssot__Subject__c, ssot__Description__c, ssot__CreatedDate__c. (Status/Priority/Origin weren't mapped - FindSimilarCases hydrates those from live CRM after the vector search, so it doesn't matter, see §2.2.)
  • RFI_Question__c_Home → create a new custom DMO. Map all 9 custom fields including Case__c.
⚠ Data Cloud renames your fields when it creates a custom DMO

In our org, mapping RFI_Question__c produced a DMO named RFI_Question_c_Home__dlm (not RFI_Question__c__dlm), with fields like Question_Text_c__c, Case_c__c, Status_c__c - Data Cloud inserts _c before the trailing __c. Your names will likely differ from ours. After mapping, confirm the actual names:

sf sobject describe --sobject <YourRfiDmoName>__dlm --target-org <alias>

Every hardcoded name in the Apex (§2) must match exactly what you see here.

1.4 Build two Search Indexes

Setup → Data Cloud → Search Indexes → New → Advanced Setup

Setting Case index RFI Question index
Search Type Hybrid Search Hybrid Search
Source Object ssot__Case__dlm (search "Case") your RFI DMO (search "RFI")
Fields to Chunk Subject, Description Question_Text_c__c, Response_Text_c__c (your names)
Embedding Model E5 Large V2 E5 Large V2
Index name pick something memorable - it becomes your table prefix

Click Review and Build, then wait for status = Ready (5–15 min). The index name determines the resulting tables: <YourIndexName>_index__dlm and <YourIndexName>_chunk__dlm. Confirm a chunk count > 0:

SELECT COUNT() FROM <YourIndexName>_chunk__dlm
Why chunk Subject + Description (not Subject alone)

In a compliance-RFI context, the regulatory detail - entity names, citations, procedural language - lives in Description, not the (often generic) Subject line. Chunking both lets a coordinator's plain words ("a regulator wants our books and records") match a Description that never uses those words but describes a books-and-records examination.

1.5 Test in Query Editor before writing any Apex

Data Cloud → Query Editor → New

SQL · Data Cloud Query Editor
SELECT v.score__c AS score, c.ssot__CaseNumber__c AS case_no, c.ssot__Subject__c AS subject
FROM vector_search(TABLE(Case_index__dlm), 'a regulator wants our books and records', '', 10) v
JOIN Case_chunk__dlm cc ON v.RecordId__c = cc.RecordId__c
JOIN ssot__Case__dlm  c  ON cc.SourceRecordId__c = c.ssot__Id__c
ORDER BY score DESC

Swap in your actual index/DMO names. You should get relevant results with no shared keywords between your query text and the matched Subject - that's proof it's working semantically, not lexically.

1.6 Permissions

Assign a Data Cloud User (or Data Cloud Admin) permission set to whichever user runs the Apex. Without it, ConnectApi.CdpQuery.queryANSISql throws an access error.

2

The Apex layer

2.1 FindSimilarCases.cls - the core pattern

The naive approach (query one Data Cloud index) misses a whole category of matches: a Case's own Subject/Description may say nothing about a topic that its RFI Questions discuss in detail (e.g. "structuring" rarely appears in a Case title, but often appears in an attached RFI question). So FindSimilarCases runs two vector searches and merges them by best score:

Apex · FindSimilarCases.cls
public with sharing class FindSimilarCases {

    private static final String CASE_INDEX = 'Case_index__dlm';
    private static final String CASE_CHUNK = 'Case_chunk__dlm';
    private static final String RFI_INDEX  = 'RFI_Question_c_Home_index__dlm'; // <- your names
    private static final String RFI_CHUNK  = 'RFI_Question_c_Home_chunk__dlm'; // <- go here

    // ... Request/Response/@InvocableMethod unchanged from the keyword-only version ...

    private static List<Id> semanticCaseSearch(String keywords, Integer limitVal) {
        Integer fetch = limitVal * 5;                 // over-fetch: one case -> several chunks
        String kw = String.escapeSingleQuotes(keywords);
        Map<Id, Decimal> best = new Map<Id, Decimal>(); // Case id -> best score from EITHER index

        // Pass 1 - match on the Case's own Subject / Description
        accumulate(best,
            'SELECT v.score__c AS rel, cc.SourceRecordId__c AS refid '
          + 'FROM vector_search(TABLE(' + CASE_INDEX + '), \'' + kw + '\', \'\', ' + fetch + ') v '
          + 'JOIN ' + CASE_CHUNK + ' cc ON v.RecordId__c = cc.RecordId__c ORDER BY rel DESC');

        // Pass 2 - match on the RFI questions attached to the Case
        accumulate(best,
            'SELECT v.score__c AS rel, q.Case_c__c AS refid '            // <- your FK field name
          + 'FROM vector_search(TABLE(' + RFI_INDEX + '), \'' + kw + '\', \'\', ' + fetch + ') v '
          + 'JOIN ' + RFI_CHUNK + ' rc ON v.RecordId__c = rc.RecordId__c '
          + 'JOIN RFI_Question_c_Home__dlm q ON rc.SourceRecordId__c = q.Id__c '  // <- your DMO name
          + 'ORDER BY rel DESC');

        List<ScoredId> ranked = new List<ScoredId>();
        for (Id cid : best.keySet()) ranked.add(new ScoredId(cid, best.get(cid)));
        ranked.sort();                                 // descending, via Comparable

        List<Id> ordered = new List<Id>();
        for (ScoredId s : ranked) { ordered.add(s.rid); if (ordered.size() >= limitVal) break; }
        return ordered;
    }
    // accumulate(), ScoredId, runCdpQuery(), hydrateOrdered(), keywordFallback() - see §2.2–§2.4
}

Search "how do we spot structuring" → the Case whose title says nothing about structuring, but whose RFI question says "detect structuring patterns", comes back ranked #1 - because its best score came from Pass 2.

2.2 Hydrate from live CRM, don't trust the DMO for display fields

Data Cloud only has the fields you mapped. Rather than adding every display field to the DMO and keeping it in sync, the pattern is: use Data Cloud only for ranking, then pull the actual record from CRM:

Apex
private static List<Case> hydrateOrdered(List<Id> ids) {
    Map<Id, Case> byId = new Map<Id, Case>([
        SELECT Id, CaseNumber, Subject, Description, Status, Priority, Origin,
               CreatedDate, ClosedDate
        FROM Case WHERE Id IN :ids
    ]);
    List<Case> ordered = new List<Case>();
    for (Id i : ids) { if (byId.containsKey(i)) { ordered.add(byId.get(i)); } }
    return ordered;
}

This also means the card always shows current data even if Data Cloud hasn't re-synced yet.

2.3 ⚠ The ConnectApi.CdpQuery row-iteration bug - and the fix

This is the single most important thing in this guide

ConnectApi.CdpQuery.queryANSISql(...) returns CdpQueryOutput.data as a List<Object> whose elements are internal ApexMapWrapper objects, not plain maps. We found, empirically:

  • output.data.size() - safe
  • Casting one element, (Map<String,Object>) output.data[0] - safe
  • Casting a second element, or iterating with a for loop - aborts the entire transaction with an opaque, uncatchable UNKNOWN_EXCEPTION…(126874768) and no debug logs at all. Happens the same way in anonymous Apex and in a real invocable call from the agent.

This will bite anyone who writes the "obvious" code:

Apex · Do not do this
// ❌ aborts with UNKNOWN_EXCEPTION as soon as you touch row 2+
for (Object row : cdpOutput.data) {
    Map<String,Object> m = (Map<String,Object>) row;   // fine on row 0, fails from row 1 on
    ...
}

The fix - copy out of the lazy collection, then round-trip each row through JSON individually:

Apex · the working pattern
private static List<Object> runCdpQuery(String sql) {
    ConnectApi.CdpQueryInput qi = new ConnectApi.CdpQueryInput();
    qi.sql = sql;
    ConnectApi.CdpQueryOutput out = ConnectApi.CdpQuery.queryANSISql(qi);

    List<Object> clean = new List<Object>();
    if (out != null && out.data != null) {
        List<Object> raw = new List<Object>();
        raw.addAll(out.data);                                  // copy out of the lazy wrapper
        for (Object row : raw) {
            clean.add(JSON.deserializeUntyped(JSON.serialize(row)));  // per-row round-trip
        }
    }
    return clean;
}

After this, clean is a plain List<Object> of plain Map<String,Object> - iterate it however you like. Every query in this project goes through runCdpQuery() - never call ConnectApi.CdpQuery.queryANSISql directly and iterate the result.

2.4 Always keep a keyword fallback

Apex
List<Id> caseIds = new List<Id>();
try {
    caseIds = semanticCaseSearch(cleaned, limitVal);
} catch (Exception e) {
    System.debug(LoggingLevel.WARN, 'vector search failed, using keyword fallback: ' + e.getMessage());
}
List<Case> caseResults = !caseIds.isEmpty()
    ? hydrateOrdered(caseIds)
    : keywordFallback(cleaned, limitVal);   // SOQL LIKE, then SOSL

If Data Cloud is down, the index isn't built yet, or the org never had Data Cloud provisioned, the agent still works - just with keyword matching. This also makes the class testable: Test.isRunningTest() short-circuits to the fallback, with an optional mockCdpRows seam to unit-test the semantic-parsing path without a real callout.

2.5 FindSimilarRfiQuestions.cls - same pattern, one index

Identical structure, single vector search against the RFI index, each result carries its parent Case (parentCaseId, parentCaseNumber) via the FK:

Apex
'SELECT v.score__c AS rel, r.Id__c AS refid '
+ 'FROM vector_search(TABLE(' + RFI_INDEX + '), \'' + kw + '\', \'\', ' + fetch + ') v '
+ 'JOIN ' + RFI_CHUNK + ' rc ON v.RecordId__c = rc.RecordId__c '
+ 'JOIN ' + RFI_DMO + ' r ON rc.SourceRecordId__c = r.Id__c '
+ 'ORDER BY rel DESC'

Built and tested, but not yet exposed as an agent action - see §3.4 to wire it up.

2.6 What we deliberately did not need

  • No callout=true on @InvocableMethod. We tested ConnectApi.CdpQuery immediately after a DML insert in the same transaction (simulating a trigger/before-save flow context) and it succeeded - the platform doesn't treat it as a blocking HTTP callout for the "uncommitted work pending" restriction. An earlier design doc for this project claimed it was required; that didn't hold up in testing. Harmless to add if you ever do see a CalloutException.
  • No Named Credential, Connected App, or Remote Site Setting - ConnectApi.CdpQuery handles its own connectivity via the org's CRM Connector.
  • No Custom Metadata Type for index names - fine for a single-org POC. If packaging for multiple customer orgs (each will name their index differently), move the index/DMO constants into a Custom Metadata Type instead of hardcoding.

Wiring into the Agentforce agent

3.1 The agent bundle

Authoring bundle: force-app/main/default/aiAuthoringBundles/RFI_Case_Analysis_Agent_Script/ (agent_type: "AgentforceEmployeeAgent", no default_agent_user needed). Two subagents, one action each:

Subagent Action target source (GenAiFunction) Output CLT
case_analysis get_case_summary apex://GetCaseSummaryFields RFI_GetCaseSummaryFields c__CaseSummaryResponse
similar_case_search find_similar apex://FindSimilarCases RFI_FindSimilarCases c__SimilarCasesResponse

3.2 ⚠ filter_from_agent - the setting that decides whether the card renders

Each action's output block has:

Agent Script · .agent
outputs:
    caseSummaryData: object
        complex_data_type_name: "c__CaseSummaryResponse"
        filter_from_agent: True     // <- must be True, not False
        is_displayable: True
Set filter_from_agent: True on both outputs

This compiles to copilotAction:isUsedByPlanner in the action's schema.

  • False → isUsedByPlanner: true → the entire action JSON is injected into the planner/LLM's context every turn. Once the model can see every field value, a request that sounds like it wants a slice of the data ("just the due date", "the answered ones") tips it into answering in prose and skipping the card - while a holistic ask ("summarize case X") still renders fine. Same wiring, inconsistent behavior.
  • True → isUsedByPlanner: false → the model never sees the payload, so it has nothing to summarize - its only option is to render the card via show_command. Verified 5/5 across a range of prompt phrasings after the fix, vs. intermittent failures before it.

is_displayable and complex_data_type_name control whether the card can render at all; filter_from_agent controls whether the model chooses to render it instead of talking about the data. The second one is the one that's easy to get backwards and hard to diagnose - it looks like "the CLT is broken" when it's actually "the model had a choice and sometimes chose text."

Trade-off: with filter_from_agent: True, the model can no longer answer follow-up questions about that data in plain text - it must re-invoke the action and re-render. Fine for a display-only card; not for conversational Q&A over the same payload.

3.4 To also expose FindSimilarRfiQuestions as an agent action

  1. Create genAiFunctions/RFI_FindSimilarRfiQuestions/ pointing invocationTarget at FindSimilarRfiQuestions.
  2. (Optional, for a rich card) Create a Custom Lightning Type + renderer LWC for SimilarRfiQuestionsResponse/SimilarRfiQuestionItem, mirroring CaseSummaryResponse/caseSummaryCard.
  3. Add a new action block to the .agent file, same shape as find_similar, with filter_from_agent: True from the start.
  4. sf agent publish (creates a new version) → sf agent activate.

3.5 Deploy → Publish → Activate

Bash
sf project deploy start --metadata AiAuthoringBundle:RFI_Case_Analysis_Agent_Script --target-org <alias>
sf agent publish authoring-bundle --api-name RFI_Case_Analysis_Agent_Script --target-org <alias>
sf agent activate            --api-name RFI_Case_Analysis_Agent_Script --target-org <alias>

Deploy puts the authoring source into the org (visible as a DRAFT in Agentforce Studio); Publish compiles it into a runnable version (also regenerates Bot/BotVersion/GenAiPlannerBundle locally); Activate makes that version live. None of the three steps do the others.

4

Testing

4.1 Three ways to run a query

  1. Query Editor (§1.5) - fastest, shows raw scores.
  2. Anonymous Apex - tests the actual class:
    Apex
    FindSimilarCases.Request req = new FindSimilarCases.Request();
req.searchKeywords = 'we are being sued and must preserve records';
req.maxResults = 5;
SimilarCasesResponse r = FindSimilarCases.findSimilarCases(
    new List<FindSimilarCases.Request>{ req })[0].similarCasesData;
System.debug(r.resultCount + ' :: ' + r.message);
for (SimilarCaseItem i : r.cases) System.debug(i.caseNumber + '  ' + i.subject);
  3. Through the agent - sf agent preview start --api-name RFI_Case_Analysis_Agent_Script, then ask e.g. "find similar cases about a regulator inspection."

4.2 Prove it's semantic, not keyword

Ask something whose words don't appear in the record it should find:

Ask Finds (no shared keywords)
we are being sued and must preserve records "Civil litigation hold – preservation of account activity logs"
evidence that customer funds are fully backed "Provide evidence of proof of reserves … asset backing"
how do we spot structuring the case whose RFI question is "…detect structuring patterns"

Contrast: SELECT Id FROM Case WHERE Subject LIKE '%being sued%' → 0 rows. Same phrase through FindSimilarCases → the right cases, ranked.

4.3 The "phrase, not keyword" rule

Vector search needs context to embed meaningfully. money laundering (2 words) returns noisy, near-random matches; anti money laundering program controls (a real phrase) returns the right AML cases at a meaningfully higher score. Coach users (and agent prompt instructions) toward short natural-language phrases, not single keywords.

4.4 Known soft spots

  • Very short queries drift - the embedding model can lock onto surface word-shape ("structuring" ≈ "structural") when there isn't enough context to disambiguate.
  • No relevance floor today - maxResults always returns that many rows even if only the #1 result is real; rows below it can be noise. Add a minimum-score cutoff in accumulate()/semanticCaseSearch() if that matters for your dataset.
  • Duplicate rows across chunks - a long record can match on 2+ of its own chunks. Both classes de-duplicate by keeping the best score per record id; ad hoc Query Editor SQL needs manual de-duping.

Differences from the original design document

An earlier planning document laid out the intended architecture. What actually shipped differs in a few places:

Plan said What we actually built/found
Migrate GetCaseSummaryFields to semantic search too Left it as pure SOQL - exact lookups don't benefit from vector search, and it's simpler/faster as-is
FindSimilarCases queries Case_index__dlm only Queries two indexes (Case text + RFI questions) and merges by best score - §2.1
FindSimilarRfiQuestions not mentioned New class we added, same pattern, single index
DMO/index names given as fixed (RFI_Question__c_index__dlm, field Question_Text__c) Names are org-specific - ours came out as RFI_Question_c_Home_index__dlm / Question_Text_c__c. Always verify with sf sobject describe (§1.3)
callout=true required on @InvocableMethod Not required in practice (§2.6) - tested calling ConnectApi.CdpQuery immediately after a DML insert in the same transaction with no CalloutException
Row iteration pattern: for (Object rowObj : cdpOutput.data) directly This exact pattern triggers the UNKNOWN_EXCEPTION bug (§2.3) once you touch more than one row - the JSON round-trip fix is not optional
No mention of CLT rendering reliability filter_from_agent must be True, or the card intermittently renders as plain text instead (§3.2) - the plan's code samples don't touch the agent-output layer at all

Complete Implementation Guide

Find Similar Cases in Salesforce

Everything in one place: how to decide between the three ways to build "find similar cases," and a full end-to-end build guide for each - the native Customer Experience Intelligence action, a custom Data Cloud RAG pipeline, and native SOSL search.

A · Out-of-the-box (Customer Experience Intelligence) B · Custom RAG (Data Cloud retriever + prompt template) C · SOSL (native full-text search)
Draws on two InfallibleTechie videos/blogs (Oct 2025, Jul 2025), Salesforce's official documentation on Data Cloud and the Find Similar Cases action, and standard SOSL/Apex patterns.
Decide

Quick answer: does a related custom object work?

Short version Yes for B and C. Not natively for A. If your resolution detail lives in a custom child object (an "RMA," a "Resolution Steps" record, an "Escalation Log"), the out-of-the-box action only ever looks at Case fields - it won't reach into a related object unless you first copy that content onto the Case. The custom RAG pipeline and SOSL both support it directly, just in very different ways: RAG treats the custom object as another source to index and ground on, SOSL just adds it to the same query's RETURNING clause.

Decide

So which one should you use?

There isn't a single right answer independent of what you already have - here's a concrete way to decide.

If you're starting from where you are today

Keep SOSL (Part C) running. It's free, real-time, and it already works - don't rip it out to chase semantics you may not need yet. The honest trigger to move past it is a measured one: track how often reps report an obviously-similar case that didn't show up because it used different words for the same problem. If that's rare, SOSL is doing its job.

When the gap is real, build Part B over Part A

If your content spans Case and a related custom object, that fact alone rules out Part A - it can't reach a custom object without a workaround. Part B costs more to build but matches your data shape and keeps programmatic access (Flow/Apex/LWC) that Part A doesn't offer.

A pragmatic middle path

Keep SOSL as an instant, zero-latency first pass, and add the Part B retriever as a second, "smarter" option surfaced only when SOSL comes back thin (fewer than 2–3 results). That gets semantic coverage without fully committing to rebuilding what already works.

Today: SOSL→ Measure recall gaps→ Gap real?→ Add Part B retriever
Part A

Out-of-the-box: Customer Experience Intelligence

The native, point-and-click path - Salesforce's built-in Find Similar Interactions action, powered by Data Cloud and the Customer Signals Intelligence add-on. No prompt template or code required.

Use case, UX & prerequisites

A rep working an open case asks Agentforce for related history and gets back closed cases that resemble it. What's different about this path is how little you build - it's a managed feature you switch on, not a pipeline you assemble field by field. In exchange for less engineering, you get less control: no prompt to write, no choice of which fields feed the model, and - as covered below - no access outside of Agentforce.

Phase 1

Lay the foundation

Two prerequisites, one of which you likely can't self-serve.

1

Enable Data Cloud

Setup → Quick Find "Data Cloud" → Data Cloud homepage

Walk through the enablement flow and wait for it to finish completely before moving on - the rest of this setup depends on Data Cloud being fully provisioned.

2

Get the Scoring Framework Admin permission set

This permission set ships with the Customer Signals Intelligence add-on. Once available: Setup → Users → [your user] → Permission Set Assignments → Edit Assignments, add Scoring Framework Admin, and save.

If you don't see itA missing Scoring Framework Admin permission set almost always means the add-on hasn't been provisioned yet - go back to your AE before troubleshooting further.
Phase 2

Activate Customer Experience Intelligence

This is the wizard that generates the rest of the pipeline for you.

3

Turn on Customer Experience Intelligence

Setup → Quick Find "Customer Experience Intelligence"
  1. Toggle the feature On.
  2. Work through the setup wizard - Topics and Agent Actions get added automatically.
  3. Make sure Case is enabled under Standard Channels.
  4. Click Activate, then wait for the confirmation email before proceeding.

Content prep note: you don't get to hand-pick fields here - your only lever is data quality. Make sure Subject and Description are actually filled in, and write real resolution detail into cases before they close. Knowledge articles aren't part of this native pipeline - that requires Part B.

Phase 3

Build the index

Same chunk-and-embed mechanics as any Data Cloud search index - just pointed at what the CXI wizard generated.

4

Schedule the Case data transform

App Launcher → Data Transforms
  1. Find the data transform auto-created for your Case channel.
  2. Open it, check the Schedule in the Details tab.
  3. Click Schedule (top right) and set the Run Mode - Scheduled or Manual.

5

Build the search index

Data Cloud → Search Index → New
Source Engagement Analysis - Analysis Text (generated by the Case transform)
Fields Manage Fields → select Engagement Analysis Payload

Freshness here is governed by the data transform's schedule (Step 4), not a setting on the index itself.

Phase 4

Expose it in Agentforce

6

Confirm the action, add the topic

Action Find Similar Cases - API name FindSimilarCases
Agent setup Agent → Topics → add the standard Customer Experience Intelligence topic

Search criteria, ranking, and result layout are handled internally by the Scoring Framework - there's no exposed UI for tuning weights or restyling the response. Test with: find similar cases for reject order.

The flexible path - build the pipeline yourself, from data stream to grounded prompt, and expose it wherever it's needed: Agentforce, Flow, Apex, or an LWC.

Phase 1

Ingest Case (and related) data into Data Cloud

1

Create the Data Stream

Data Cloud → Data Streams → New
Source Salesforce CRM · View objects (not bundles)
Object Case (standard) - plus a second stream for any related custom object
Fields Id, CaseNumber, Subject, Description, IsClosed
Filter IsClosed = true - index only cases with a known outcome
2

Map the DLO to the standard Case DMO

Map each DLO field to the standard Case DMO - this mapping is the "harmonization" that makes Case rows queryable and indexable.

Bringing in a related custom object

Two ways to include it:

  • Combine at harmonization - concatenate its text onto the Case DMO's searchable field, or join it in via Data Cloud's relationship capability, so one retriever covers both. Best for a short, near-1:1 related record.
  • Index separately, ground on both - build a second DMO, index, and retriever for the custom object, and reference both retrievers from one Flex prompt template. Best for a one-to-many relationship or structurally different content.

Preparing content for semantic search

  • Combine Subject and Description conceptually - Subject alone is usually too short to embed meaningfully.
  • Prefer one comprehensive text field over several partial ones - chunking works better against one coherent passage.
  • Strip boilerplate and PII before indexing where possible.
  • For Knowledge articles, index the body (not just the title), use headings/paragraph structure for cleaner chunking, and convert tables to JSON/HTML before chunking.
Common mistakeIndexing every text field "just in case" produces noisy chunks and slower, less relevant retrieval.
Phase 2

Build the semantic search index

3

Create the Search Index

Data Cloud → Search Index → New → Advanced
Source DMO Case
Index type Vector for pure semantic matching, or Hybrid if reps also search exact terms (order numbers, SKUs)
Fields Id, CaseNumber, Subject, Description

Save and monitor until status reads Completed. Freshness: the data stream refresh controls how often new rows land; the search index refresh re-embeds incrementally - only what changed, not the whole corpus each time.

4

Create an Individual Retriever

Einstein Studio → Retrievers → New Retriever → Individual Retriever
Source Data Cloud → your Data Space → Case DMO → the index from Step 3
Output fields CaseNumber, Subject, Description, Id
Top-K 5 results

Ranking is driven by vector similarity score - you don't hand-tune a formula, but you do control eligibility via filters (e.g. IsClosed = true) and field selection. Don't just raise top-K to fix missing results - the fix is almost always better field selection or chunking.

Phase 3

Ground a prompt template

5

Build the Flex Prompt Template

Setup → Prompt Builder → New Prompt Template → Flex
prompt text
Search {!$Input:Search_String} in {!$EinsteinSearch:Similar_Case_Retriever.results} List up to 5 similar closed cases as a bulleted list. For each, show the case number as a hyperlink, followed by a short phrase describing what it was about. If no relevant cases are found, say so plainly.
Rich text mattersWherever this renders, use rich text - not plain text - or case links show up as raw URLs the rep has to copy.

Click Activate once it works - this exposes it as an invocable action to Flow, Apex, the REST API, and Agentforce.

Phase 4

Expose it: Agentforce, Flow, Apex, or LWC

6

Wire it into Agentforce

Action New Action → Reference type: Prompt Template → your template → output rendering: Rich text
Use the Find Similar Cases action whenever the user asks to find similar, related, or comparable cases. Display the result in rich text format only.
7

Or invoke it from Flow, Apex, or an LWC

Flow: Action element → category Prompt Template → your template → map Subject/Description into Search_String, display in a rich-text screen component.

apex
ConnectApi.EinsteinPromptTemplateGenerationsInput req = new ConnectApi.EinsteinPromptTemplateGenerationsInput(); req.isPreview = false; Map<String, ConnectApi.WrappedValue> inputParams = new Map<String, ConnectApi.WrappedValue>(); ConnectApi.WrappedValue searchInput = new ConnectApi.WrappedValue(); searchInput.value = caseRecord.Subject; inputParams.put('Input:Search_String', searchInput); req.inputParams = inputParams; ConnectApi.EinsteinPromptTemplateGenerationsRepresentation resp = ConnectApi.EinsteinLLM.generateMessagesForPromptTemplate( 'Find_Similar_Cases_Prompt', req ); String similarCasesText = resp.generations[0].text;

LWC: wrap the Apex above in an @AuraEnabled method and call it from the component. REST: the same template is reachable at /einstein/prompt-templates/Find_Similar_Cases_Prompt/generations.

Part C

SOSL: native full-text search

No Data Cloud, no add-on, no index to build - Salesforce's built-in search index, queried directly. The fastest path to "good enough," with a real ceiling on how "smart" it can get.

How it works

SOSL (Salesforce Object Search Language) queries Salesforce's own full-text search index - the same index behind Global Search. It's a lexical, keyword-based match, not a semantic one: it finds records containing the words you searched for (with some stemming and fuzziness), not records that mean the same thing using different words. Its standout strength for this use case is native multi-object search - one query can return matches from Case and a related custom object at the same time.

1

Write the SOSL query

FIND {reject order} IN ALL FIELDS RETURNING Case(Id, CaseNumber, Subject, Description WHERE IsClosed = true ORDER BY LastModifiedDate DESC LIMIT 10), Resolution__c(Id, Name, Summary__c, Case__c WHERE Case__c != null LIMIT 10)

Fields you search on need to be marked Searchable, and results respect field-level security and sharing - SOSL never returns data the running user couldn't otherwise see.

2

Wrap it in Apex, correlate the results

String searchTerm = String.escapeSingleQuotes(caseRecord.Subject); List<List<SObject>> results = [ FIND :searchTerm IN ALL FIELDS RETURNING Case(Id, CaseNumber, Subject, Description WHERE IsClosed = true ORDER BY LastModifiedDate DESC LIMIT 10), Resolution__c(Id, Name, Summary__c, Case__c LIMIT 10) ]; List<Case> similarCases = (List<Case>) results[0]; List<Resolution__c> relatedResolutions = (List<Resolution__c>) results[1]; // Correlate: match Resolution__c.Case__c back to a Case.Id // to build one combined, ranked result set.

Expose this as an @InvocableMethod to make it callable from Flow, or as an @AuraEnabled method for an LWC - either way, it's the same pattern as the Apex path in Part B, just backed by SOSL instead of a prompt template.

3

Surface it: Flow, LWC, or a Quick Action

  • Flow: call the @InvocableMethod from an Autolaunched or Screen Flow, e.g. triggered on case creation, and display results in a related list or screen component.
  • LWC: call the @AuraEnabled method from a custom sidebar or record-page component for a bespoke results panel.
  • Agentforce: also possible - wrap the Apex in an invocable action and register it as a custom Agent Action, giving you a conversational front end without Data Cloud at all.

Ranking & tuning, since it's manual here

  • Relevance - SOSL returns matches in the order Salesforce's search engine scores them (term frequency, field weighting), but for genuine control you'll typically re-sort in Apex - e.g. boost exact phrase matches, or weight matches in Subject higher than matches in Description.
  • Recall vs. precision - broaden with FIND {reject* order*} wildcarding if too few results come back; narrow with more specific phrases or additional WHERE filters if too many do.
  • Synonyms are your responsibility - if "cancelled" and "rejected" should both match, you either maintain a synonym group in Salesforce Setup, or expand the search term programmatically before querying.
  • This is the ceiling - no amount of query tuning gives SOSL true conceptual matching. If you hit that wall consistently, that's the signal to add Part B rather than keep tuning Part C.

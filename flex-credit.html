Part 1 · All users

DLO Discovery & Reporting

The master reference for all six DLOs behind Agentforce Flex Credit — what each one contains, the platform rules that apply before you query any of them, and the discovery-first workflow that keeps you out of "unknown column" errors.

Data Cloud · Query Editor Production org only SQL, not SOQL

What are DLOs?

DLOs (Data Lake Objects) are Salesforce-managed tables inside Data Cloud that store your Agentforce Flex Credit usage data. Think of them as the raw ledger behind everything the Digital Wallet UI shows you.

When an agent is deployed to production, every interaction is recorded as an event in these tables. Querying the DLOs directly lets you build custom reports with any filter, grouping, or date range you need — without relying on the out-of-the-box Digital Wallet.

Where to run these queries

Go to Data Cloud → Query Editor in your production org. DLO queries do not run in Developer Console, Workbench, or sandboxes. Usage is tracked across every environment, but only visible through production.

Each DLO serves a different reporting purpose and carries a different access sensitivity. Use this table to decide which object you need before writing a query.

__dll suffix required

In Data Cloud Query Editor, every DLO table name needs the __dll suffix — e.g. TenantEnrichedUsageEvent__dll. Without it, the query returns "table not found."

Platform rules — read before querying

  • Query Editor only. Data Cloud → Query Editor, using the default Data Space. This is SQL, not standard SOQL.
  • Production org only. You cannot view consumption data from a sandbox.
  • Always run discovery first. Column names can vary between orgs. Run SELECT * FROM <table>__dll LIMIT 5 before any filtered query.
  • Retention was observed at 730 days in this org as of testing (September 2026). Retention windows are configurable per org / data space — confirm your org's current setting in Data Cloud Setup rather than treating this as a fixed platform limit.
Critical — cardname__c does not exist on TDEC

TenantDailyEntitlementConsumption__dll does not have a cardname__c column. Running WHERE cardname__c = 'Flex Credits' causes:

Always run the discovery query first to see which filter columns actually exist in your org.

Manager entitlement query
Daily burn rate — allocation pulled dynamically from TET · manager access required
Manager / admin access required

This query accesses TDEC, which reflects your purchased credit allocation and remaining balance. Restrict to manager and admin users only.

Because TDEC tracks daily consumption logs — not a running allocation balance — the allocated credit limit is pulled dynamically from TenantEntitlementTransaction__dll using a CTE. No hardcoded values needed.

Option 1 — dynamic subquery (global total)

SQL · Global total
WITH total_allocation AS (
    SELECT COALESCE(SUM(quantity__c), 0) AS allocated_credits
    FROM TenantEntitlementTransaction__dll
),
base_usage AS (
    SELECT
        utilizationdate__c   AS report_date,
        unitsconsumed__c     AS consumed_credits
    FROM TenantDailyEntitlementConsumption__dll
    WHERE utilizationdate__c >= CURRENT_DATE - INTERVAL '90' DAY
      AND unitsconsumed__c > 0
)
SELECT
    u.report_date, a.allocated_credits, u.consumed_credits,
    (a.allocated_credits - u.consumed_credits)                            AS remaining_credits,
    ROUND((u.consumed_credits / NULLIF(a.allocated_credits, 0)) * 100, 1) AS pct_consumed
FROM base_usage u
CROSS JOIN total_allocation a
ORDER BY u.report_date DESC;

Option 2 — join by specific credit card type

SQL · By card type
WITH card_allocations AS (
    SELECT entitlementcarddefdevlname__c AS card_name, SUM(quantity__c) AS allocated_credits
    FROM TenantEntitlementTransaction__dll
    GROUP BY entitlementcarddefdevlname__c
)
SELECT
    c.utilizationdate__c                                                   AS report_date,
    a.allocated_credits,
    c.unitsconsumed__c                                                     AS consumed_credits,
    (a.allocated_credits - c.unitsconsumed__c)                             AS remaining_credits,
    ROUND((c.unitsconsumed__c / NULLIF(a.allocated_credits, 0)) * 100, 1)  AS pct_consumed
FROM TenantDailyEntitlementConsumption__dll c
JOIN card_allocations a ON c.carddefinitiondevelopername__c = a.card_name
WHERE c.utilizationdate__c >= CURRENT_DATE - INTERVAL '90' DAY
  AND c.unitsconsumed__c > 0
ORDER BY c.utilizationdate__c DESC;

Build the report in Report Builder
Turn a verified query into a shareable Salesforce report
  1. Go to Reports tab → New Report.

    From the App Launcher in your production org, navigate to Reports and click New Report.

  2. Select report type: Data Cloud.

    In the category picker, scroll to Data Cloud and choose it as your report type.

  3. Choose your primary object.

    Developer report: select TenantEnrichedUsageEvent. Manager report: select TenantDailyEntitlementConsumption.

  4. Add fields from the field picker.

    Drag in the fields confirmed during discovery: date field, usage type, credits, and any calculated columns.

  5. Set your filters.

    For TEUE: usagetypedevelopername__c != SpeechFoundations_Translation. For TDEC: add a date range filter on utilizationdate__c.

  6. Group and summarize.

  7. Run and verify.

    Confirm totals match what you saw in Query Editor.

  8. Save to a shared folder.

    Save → name the report → choose the correct folder. To share with non-admin users, the folder only needs Run Reports permission.

No elevated permissions needed for the developer report

Security boundary — what's included vs. excluded

This report deliberately includes only consumption data and excludes all contract and billing information. Keeping this boundary intact is what makes it safe to share broadly.

Developer report security boundary — TenantEnrichedUsageEvent only

Why this solves the access problem

The Digital Wallet requires elevated permissions that can trigger Security Center alerts. A report built from TenantEnrichedUsageEvent contains only consumption fields — no contract data — so it can be shared via a standard report folder with just Run Reports. No elevated access required.

3
Burn rate query
% of allocation consumed per day — confirmed working

Pulls the contracted allocation dynamically from TenantEntitlementTransaction__dll via a CTE — no hardcoded values. Uses a CROSS JOIN to attach the total allocation to every daily row before calculating burn rate.

Verified working query

Allocation is pulled live from TenantEntitlementTransaction__dll using COALESCE(SUM(quantity__c), 0) — stays accurate as the contract is renewed or topped up.

SQL · Verified
WITH total_allocation AS (
    -- Dynamically calculate total contracted allocation
    SELECT COALESCE(SUM(quantity__c), 0) AS allocated_credits
    FROM TenantEntitlementTransaction__dll
),
base_usage AS (
    SELECT
        c.utilizationdate__c                                  AS report_date,
        c.unitsconsumed__c                                    AS consumed_credits,
        a.allocated_credits
    FROM TenantDailyEntitlementConsumption__dll c
    CROSS JOIN total_allocation a
    WHERE c.utilizationdate__c >= CURRENT_DATE - INTERVAL '90' DAY
      AND c.unitsconsumed__c > 0
)
SELECT
    report_date,
    allocated_credits,
    consumed_credits,
    (allocated_credits - consumed_credits)                             AS remaining_credits,
    ROUND((consumed_credits / NULLIF(allocated_credits, 0)) * 100, 1) AS pct_consumed
FROM base_usage
ORDER BY report_date DESC;
4
Projected exhaustion query
When will credits run out at the current burn rate?
Exhaustion formula
Texhaust = today + (remaining_credits ÷ avg_daily_burn) days
The 30-day window smooths weekday/weekend variance. Use a 7-day rolling average if consumption has strong weekly cycles.

Query A — current remaining balance

Field name correction

entitledunits__c does not exist on TDEC, and the consumed-credits field is unitsconsumed__c — not consumedunits__c. Both queries below use the correct field names.

Option 1 — single-day remaining (most recent day only)

SQL · Option 1 — single day
WITH total_allocation AS (
    SELECT COALESCE(SUM(quantity__c), 0) AS total_credits
    FROM TenantEntitlementTransaction__dll
),
latest_usage AS (
    SELECT
        utilizationdate__c,
        unitsconsumed__c
    FROM TenantDailyEntitlementConsumption__dll
    ORDER BY utilizationdate__c DESC
    LIMIT 1
)
SELECT
    u.utilizationdate__c                       AS as_of_date,
    (a.total_credits - u.unitsconsumed__c)     AS remaining_credits
FROM latest_usage u
CROSS JOIN total_allocation a;

Option 2 — cumulative contract balance (recommended for exhaustion projection)

SQL · Option 2 — cumulative balance
WITH total_allocation AS (
    SELECT COALESCE(SUM(quantity__c), 0) AS total_credits
    FROM TenantEntitlementTransaction__dll
),
summary AS (
    SELECT
        MAX(utilizationdate__c)   AS as_of_date,
        SUM(unitsconsumed__c)     AS total_consumed
    FROM TenantDailyEntitlementConsumption__dll
)
SELECT
    s.as_of_date,
    s.total_consumed,
    (a.total_credits - s.total_consumed) AS remaining_credits
FROM summary s
CROSS JOIN total_allocation a;
Which option should I use?

Option 1 — "How many credits were left at the end of yesterday?" — a dashboard number tile.

Option 2 — "How many credits remain in my total contract?" — use this remaining_credits value in Query C below.

Query B — average daily burn (last 30 days)

SQL · Verified
SELECT
    ROUND(AVG(unitsconsumed__c), 0)  AS avg_daily_burn
FROM TenantDailyEntitlementConsumption__dll
WHERE utilizationdate__c >= CURRENT_DATE - INTERVAL '30' DAY;

Query C — projected exhaustion date (single combined query)

Combines cumulative remaining balance and 30-day average burn using two CTEs with a CROSS JOIN. Returns one row with today's date, remaining credits, average daily burn, and days until exhaustion. Confirmed working.

SQL · Verified
WITH total_allocation AS (
    SELECT COALESCE(SUM(quantity__c), 0) AS total_credits
    FROM TenantEntitlementTransaction__dll
),
total_consumed AS (
    SELECT COALESCE(SUM(unitsconsumed__c), 0) AS total_consumed
    FROM TenantDailyEntitlementConsumption__dll
),
daily_burn AS (
    SELECT AVG(unitsconsumed__c) AS avg_daily_burn
    FROM TenantDailyEntitlementConsumption__dll
    WHERE utilizationdate__c >= CURRENT_DATE - INTERVAL '30' DAY
)
SELECT
    CURRENT_DATE                                                                AS today,
    (a.total_credits - c.total_consumed)                                       AS remaining_credits,
    ROUND(b.avg_daily_burn, 1)                                                 AS avg_daily_burn,
    FLOOR((a.total_credits - c.total_consumed) / NULLIF(b.avg_daily_burn, 0))  AS days_until_exhaustion
FROM total_allocation a
CROSS JOIN total_consumed c
CROSS JOIN daily_burn b;

Manager entitlement query — dynamic allocation
Allocation pulled live from TenantEntitlementTransaction — no hardcoded values

Because TDEC tracks daily consumption logs, not a running allocation balance, the credit limit is pulled dynamically from TET using a CTE.

Option 1 — dynamic global total

Use when your org has a single credit pool.

SQL · Global total
WITH total_allocation AS (
    SELECT COALESCE(SUM(quantity__c), 0) AS allocated_credits
    FROM TenantEntitlementTransaction__dll
),
base_usage AS (
    SELECT
        utilizationdate__c   AS report_date,
        unitsconsumed__c     AS consumed_credits
    FROM TenantDailyEntitlementConsumption__dll
    WHERE utilizationdate__c >= CURRENT_DATE - INTERVAL '90' DAY
      AND unitsconsumed__c > 0
)
SELECT
    u.report_date, a.allocated_credits, u.consumed_credits,
    (a.allocated_credits - u.consumed_credits)                            AS remaining_credits,
    ROUND((u.consumed_credits / NULLIF(a.allocated_credits, 0)) * 100, 1) AS pct_consumed
FROM base_usage u
CROSS JOIN total_allocation a
ORDER BY u.report_date DESC;

Option 2 — join by specific credit card type

Use when your org has multiple credit types. Join key: TET.entitlementcarddefdevlname__c = TDEC.carddefinitiondevelopername__c.

SQL · By card type
WITH card_allocations AS (
    SELECT entitlementcarddefdevlname__c AS card_name, SUM(quantity__c) AS allocated_credits
    FROM TenantEntitlementTransaction__dll
    GROUP BY entitlementcarddefdevlname__c
)
SELECT
    c.utilizationdate__c                                                   AS report_date,
    a.allocated_credits,
    c.unitsconsumed__c                                                     AS consumed_credits,
    (a.allocated_credits - c.unitsconsumed__c)                             AS remaining_credits,
    ROUND((c.unitsconsumed__c / NULLIF(a.allocated_credits, 0)) * 100, 1)  AS pct_consumed
FROM TenantDailyEntitlementConsumption__dll c
JOIN card_allocations a ON c.carddefinitiondevelopername__c = a.card_name
WHERE c.utilizationdate__c >= CURRENT_DATE - INTERVAL '90' DAY
  AND c.unitsconsumed__c > 0
ORDER BY c.utilizationdate__c DESC;
Which option should I use?

Option 1 — single credit pool, simple global total. Option 2 — multiple credit card types, each calculated against its own allocation limit.

Purchased credits, dates, buying model — Finance / Manager only
Sensitive — Finance / Manager only

Returns contract terms including purchased quantities, start/end dates, and buying model. Do not share with developers or general users.

SQL · Finance / Manager only
SELECT
    entitlementcarddefdevlname__c        AS card_name,

    Required if your org uses custom consumption tags.
  • Data Cloud Data Access
    Read access to Data Cloud objects and DLO schemas. Required to build and run custom reports against entitlement DLOs.
  • Manage Flow / Run Flows
    Required only if this user also manages Consumption Threshold Alert flows. Optional for read-only dashboard viewers.

Governance recommendations

  • Create a dedicated Public Group (e.g., "Flex Credit Dashboard Viewers") for all manager and finance users who need access.
  • Share the manager report folder with this Public Group only — never with "All Internal Users."
  • Audit access quarterly to ensure only authorized stakeholders have visibility into contract and budget data.
  • Never combine developer and manager reports in the same folder — separate folders, separate sharing rules.
  • When onboarding new finance or manager users, assign permission sets explicitly — do not rely on profile-level defaults.
Never merge these two reports

The developer consumption report (TEUE) and the manager entitlement dashboard (TDEC + TET) must remain in separate folders with separate sharing rules. Merging them would expose contract terms to developers — a data governance violation.

Custom Lightning Type & LWC Rendering Checklist

Every requirement that determines whether a Custom Lightning Type actually renders in Agentforce — or silently falls back to plain text. Mandatory items are marked must; everything else is a recommendation or convention. When in doubt, treat a missing mandatory item as the reason nothing is showing up.

Cross-checked against Salesforce's official Agentforce & Lightning Types developer documentation. Anywhere this build's actual (working) code diverges from Salesforce's documented recommendation, it's called out explicitly rather than silently corrected — see the callout in Metadata & configuration and the sources listed in the footer.

// read this first

🔴 Critical — the 5 rules that cause silent failures

These five are singled out because getting them wrong produces no error message. The org deploys cleanly, the action runs, and the platform just quietly falls back to plain-text conversation or a broken form. If a CLT "isn't working," check these before anything else.

1

The agent script must contain the literal phrase "user_input tool"

Write Call {!@actions.create_lead} action's user_input tool to collect the lead details from the user. The platform parses the instruction text for that exact phrase — it's the signal that activates the CLT editor lookup pipeline (finds the Lightning Type → editor.json → the LWC). Paraphrasing it ("collect the lead details", "ask the user for their info") leaves every other piece perfectly wired and simply unused — the agent falls back to asking for fields one at a time in plain text.

2

Apex wrapper field names must exactly match the action's parameter names

The request/response wrapper class field names (e.g. lead_data, lead_result, lead_id, lead_name) are matched by name against the agent action's input/output parameters. A mismatch throws no error — the field just comes back null, or the whole action silently falls back to the plain-text UI.

3

The editor must dispatch the entire value object on every change — never a single field

Sending { detail: { lastName: 'Smith' } } instead of { detail: this.value } makes the platform treat every other field as unset — it doesn't merge, it replaces. This is the single most common way a CLT form "loses" data the user already typed.

4

targetType and sourceType are not interchangeable

The editor's (input) js-meta.xml uses <targetType name="c__X"/>. The renderer's (output) js-meta.xml uses <sourceType name="c__X"/>. Use the wrong one and Setup won't correctly bind that component to that role, even though the XML is otherwise valid.

5

Four flags must all be true, or that direction never activates

isExposed (meta XML, both components) · is_user_input (action input) · is_displayable (action output) · and in the Agent Action asset UI, Collect data from user / Show in conversation respectively. Any one left false silently disables CLT rendering for that side, even with a correctly built component sitting right there.

Custom Lightning Type requirements

A Lightning Type is a JSON-based schema definition that binds an Apex data shape to an LWC. Two are needed per action — one for what the form collects, one for what the card displays — and each is built and configured separately.

RequirementDetail
Separate type per directionOne Lightning Type for the input shape, one for the output shape. They are not interchangeable and not combinable into one type.must
Apex-based schemaSetup → Lightning Types → New → source Apex → search and select the Apex inner class. The Apex class must already be deployed or it won't appear in the picker.must
Class addressed as Outer$Innere.g. LeadCreationService$LeadInput — Salesforce's nested-class reference syntax. Get the outer/inner names wrong and the schema can't resolve.must
c__ namespace prefixEvery reference to the type elsewhere (meta XML, agent script, Agent Action asset) uses the type's API name prefixed with c__, e.g. c__LeadInput. Missing or wrong prefix = type not found.must

UI Configuration → Renderer overrideOn the output type: UI Configuration → Renderer tab → override with your renderer LWC. Left unset, output renders as the generic/standard card.must
Live Component PreviewBoth override screens show a live preview once saved — use it to confirm the real component (not the standard one) is what's wired before moving on.recommended

LWC requirements

Every rendering-relevant rule an Editor or Renderer component must follow. Miss one and the platform doesn't throw — it just doesn't wire the component in.

Shared by both components

Renderer (Output)must

target: lightning__AgentforceOutput
targetConfig uses sourceType (not targetType) with name="c__LeadOutput"
@api value — a single property, no getter/setter pair required

Null-safe getters (this.value?.field || '') recommended so missing data renders blank, not "undefined"

⚠️

The one-field dispatch trap

The editor's valuechange handler must merge the changed field into local state and dispatch the whole object — detail: this.value, not detail: { fieldName: newValue }. Dispatching a partial object doesn't error; it makes the platform treat every field you didn't include as cleared.

Reference meta XML — Editor

<targetConfig targets="lightning__AgentforceInput">
    <targetType name="c__LeadInput" />
</targetConfig>

Reference meta XML — Renderer

<targetConfig targets="lightning__AgentforceOutput">
    <sourceType name="c__LeadOutput" />
</targetConfig>

Required files & folder structure

Seven artifacts, minimum, for one working CLT-powered action. Missing any one leaves the pipeline incomplete even if everything else is correct.

📁

editor.json / renderer.json live one level deeper than you'd expect

Per Salesforce's Lightning Types bundle spec, editor.json and renderer.json are not siblings of schema.json — they sit inside a channel-specific subfolder (lightningDesktopGenAi for an Agentforce Employee/Lightning Experience agent, enhancedWebChat for a Service agent on Enhanced Chat v2, lightningMobileGenAi for mobile, experienceBuilder for Experience Builder — note renderer.json isn't supported there). Only schema.json is mandatory in every bundle; the override files are channel-scoped. Building via the Setup UI (as this guide does) creates this structure for you — hand-authoring the metadata without the channel folder is the mistake to avoid.

force-app/main/default/ classes/ LeadCreationService.clsMUST — input shape, output shape, request wrapper, response wrapper, 1 @InvocableMethod lightningTypes/ (or built via Setup UI — functionally identical) LeadInput/ schema.jsonMUST lightningDesktopGenAi/— channel folder editor.jsonMUST LeadOutput/ schema.jsonMUST lightningDesktopGenAi/— channel folder renderer.jsonMUST lwc/ leadInputEditor/ leadInputEditor.jsMUST leadInputEditor.htmlMUST leadInputEditor.js-meta.xmlMUST leadResultRenderer/ leadResultRenderer.jsMUST leadResultRenderer.htmlMUST leadResultRenderer.js-meta.xmlMUST

schema.json — the actual Apex binding

This is the file that makes a Lightning Type be something — it's what the Setup UI writes for you when you pick an Apex class in the "New Lightning Type" modal. The binding is a JSON Schema document whose lightning:type keyword points at the Apex class via the @apexClassType/ prefix:

{
  "title": "Lead Input",
  "description": "Lead Input",
  "lightning:type": "@apexClassType/c__LeadCreationService$LeadInput"
}

The c__ segment is the namespace prefix — always c for classes local to your org, regardless of the org's own namespace; a managed package uses its registered namespace instead. The $ is the outer/inner class separator Setup itself generates when you point a Lightning Type at a nested Apex class (this is the schema-binding syntax observed from the org, not something Salesforce's official docs document — see the divergence callout below, since those docs recommend avoiding nested classes entirely). The full @apexClassType/… string is what lands in schema.json; the bare c__LeadInput form — the Lightning Type's own API name — is what's referenced by complex_data_type_name and by targetType/sourceType in the LWC's meta XML.

🔗

The Agent Action asset is not optional

Even when the CLT experience is authored entirely through an agent script, Agentforce still requires a first-class Agent Action asset referencing the Apex invocable method. Skipping it because "the script already calls the Apex method" is a common oversight — the script calls the asset, not the Apex method directly.

⚠️

Where this guide's build diverges from Salesforce's official Apex-Based Lightning Types docs

This guide's Apex service class nests four inner classes (LeadInput, LeadResult, CreateLeadRequest, CreateLeadResponse) as public members of one outer class, addressed in Setup as LeadCreationService$LeadInput. It deployed and rendered correctly. Salesforce's official Apex-Based Custom Lightning Types guide instead directs developers to: define every class as a top-level class in its own file ("don't use nested/inner classes"), mark every class global rather than public ("using public or private can cause failures in namespaced orgs or managed packages"), and add @AuraEnabled + @JsonAccess as above. Treat the nested/public pattern as what worked in a non-namespaced dev org for this build — not as Salesforce's recommended pattern. If you see a Lightning Type silently fail to bind, or it works in a scratch/dev org but not in a namespaced org or managed package, switching to top-level global classes with these annotations is the official fix to try.

Deployment requirements

CLT pieces have real dependencies on each other — deploying out of order causes "can't find that class/component" errors that have nothing to do with the code itself.

DependencyWhy the order matters
Apex before Lightning TypesThe New Lightning Type picker searches already-deployed Apex classes by name — an undeployed class simply won't appear.
LWCs before override configurationThe Editor/Renderer override picker only lists components that are deployed, isExposed, and carry the matching target.
Lightning Types + LWCs before the Agent Action assetInput/Output Rendering dropdowns on the asset are populated from existing Lightning Types.
Agent Action asset before the agent script references itThe script pulls the action in from the asset library — there's nothing to pull in otherwise.
Any Apex field renameRe-sync it everywhere: the wrapper field name, the agent script parameter name, and (if it's a schema field) the Lightning Type stays correct automatically since it points at the class, but any hardcoded references do not.
🔡

Lowercase convention

Keep every script-level identifier — action names, variable names, labels — lowercase. It's the convention the tooling was built and tested against; inconsistent casing is a common, hard-to-spot source of reference mismatches (see Critical Rule #2).

Pre-deployment checklist

Apex
  • Input data-shape class fields all carry @InvocableVariable required=true set on any field that should be mandatory on the form
  • Request wrapper's single field is annotated @InvocableVariable(required=true) and named to match the agent action's input parameter
  • Response wrapper field names match the agent action's output parameter names exactly
  • Exactly one @InvocableMethod, static, List<Request> → List<Response>
  • Class deployed successfully before attempting to create a Lightning Type from it
  • If deploying beyond a scratch/dev org — top-level (non-nested) global classes with @AuraEnabled and @JsonAccess Salesforce's official pattern; this build's nested/public classes worked in a dev org but aren't the documented recommendation
Lightning Types
  • Input Lightning Type created, schema = Outer$InputInnerClass
  • Output Lightning Type created, schema = Outer$OutputInnerClass
  • Both API names noted with their c__ prefix for use everywhere else
  • If hand-authoring metadata (not using the Setup UI): editor.json/renderer.json placed inside the correct channel subfolder (lightningDesktopGenAi, enhancedWebChat, etc.), not as a sibling of schema.json
LWCs
  • Editor: isExposed=true, target=lightning__AgentforceInput, targetType name="c__…"
  • Editor: @api readOnly and @api value (getter/setter) both present
  • Editor: change handler dispatches valuechange with the full merged object every time
  • Renderer: isExposed=true, target=lightning__AgentforceOutput, sourceType name="c__…"
  • Renderer: @api value present, getters use null-safe fallbacks
  • Both components deployed successfully
  • Editor override set on the input Lightning Type's UI Configuration; live preview confirms it
  • Renderer override set on the output Lightning Type's UI Configuration; live preview confirms it
Agent Action asset
  • Created via Apex → Invocable Method → the correct method selected
  • Input: Require input and Collect data from user checked; Input Rendering set to the input Lightning Type
  • Output: Show in conversation checked on the displayable output; Output Rendering set to the output Lightning Type
  • Any output that should stay hidden from the conversation (like a raw ID) left unchecked
Agent script
  • Action pulled in from the asset library, not hand-typed
  • Action name identical in reasoning.actions.X and the actions.X definition
  • Action's source value matches the Agent Action asset's GenAiFunction developer name exactly
  • Reasoning instructions contain the literal phrase "user_input tool", referencing the action
  • All identifiers lowercase
  • Tested via Preview: form appears on the first relevant message, submitting returns the styled card

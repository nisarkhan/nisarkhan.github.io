Document AI and Prompt Builder file inputs

Questions that come up whenever a Salesforce design touches a PDF, answered in order.

What is the difference between Agentforce Prompt Builder reading a document and Data Cloud Document AI?

They solve two different problems that happen to start with the same PDF. One turns a document into fields. The other lets a model read a document and talk about it.

Document AI lives in Data Cloud, now branded Data 360, and is intelligent document processing. It uses LLMs to extract structured data from unstructured documents such as invoices, resumes, lab reports, and purchase orders. You start with a schema configuration: pick the document type, choose the model, upload sample documents, then auto-extract or hand-define the fields. The schema is the contract, so every document of that type comes back with the same typed fields. It supports real-time mode, invoking the API directly for documents stored in Salesforce or sent at run time, and batch mode, which processes large volumes from external sources through unstructured data model objects.

Prompt Builder file inputs are multimodal prompting, not extraction. Since Spring '25 you can pass files into a prompt template, either as a File object when invoking programmatically from Apex, an LWC, REST, or an Agentforce action, or by putting the file on a record's Notes and Attachments. Supported types include PNG, JPEG, and PDF on models that accept them, and the model limitations panel in the template config shows the real ceilings on file size and count. The output is text: a summary, an email draft, a generated field value.

When should I use one over the other, with a real example?

If the answer is a value something downstream consumes, extract it. If the answer is a judgment a human reads once, generate it.

Provider credentialing packets, use Document AI

A payer receives credentialing packets through an SFTP drop that lands in S3, a few thousand a month. Each contains an NPI, a state license number, a license expiration date, and a malpractice coverage amount. Those dates drive a renewal workflow and a quarterly compliance report.

The document type repeats, the fields are known, and downstream automation needs real values. A connector ingests the S3 folder, a UDLO references the files, batch mode extracts against the schema into a DLO, the DLO maps to a DMO, and a Flow updates Provider records. The packets never become files in the org.

A prompt template would be the wrong tool: thousands of full PDFs through an LLM every month, no guarantee a field is named the same way twice, and no batch path.

A doctor's letter on a case, use a Prompt Builder file input

A member attaches a three page letter from their physician to a case, explaining why an out of network referral is medically necessary. The agent needs to know what is being asked and what is missing before routing it.

Every letter is different and no stable field set exists. A Flex prompt template takes the case record plus the attached file and returns a summary and a suggested next step, surfaced as an agent action or a button on the case.

Document AI would be the wrong tool here: a week spent defining a schema for a document type that has no shape, and it breaks on the first letter that does not follow the pattern.

The gray zone, which is where most requirements actually sit

The document type repeats, but the output people want is a judgment. Lab reports, contracts, claims correspondence. The answer is both, in sequence: Document AI extracts once into structured fields, then a prompt template grounds on those fields and related records rather than on the raw PDF. The generation step gets cheap, repeatable context and the expensive document read happens exactly once.

Worked example: a prior authorization packet

A member uploads a six page prior auth packet to an Experience Cloud site. Run it both ways and the division of labor becomes obvious.

With Document AI: you build a schema for "prior auth packet" with member ID, date of service, diagnosis codes, requesting provider NPI, and requested units. Every packet comes back with those same fields and a Flow writes them onto the case and the member record. If a field is missing you know exactly which one, because the schema said it should be there. This is the version you can report on and audit six months later.

With a prompt template file input: a Flex template takes the packet plus the case record and returns a short clinical summary for the reviewer, covering what is being requested, for whom, and what is missing. Genuinely useful to a human, and not something you would want to store in a numeric field or run a report against.

What most orgs actually build: both. Document AI does the extraction, and the prompt template reads the extracted data plus the case to write the reviewer summary or the member response. Extraction feeds generation.

The combined pattern

  1. Document lands in Salesforce or is ingested into Data Cloud through a connector.
  2. Document AI runs against its schema configuration and returns typed fields.
  3. Flow or Apex maps those fields onto records, or they land in a data lake object and get mapped to a DMO.
  4. A prompt template grounds on the record and the DMO, not on the raw PDF, and generates the summary, email, or next best action.
  5. The agent calls that prompt template as an action, with clean and cheap context instead of a whole document in every turn.

The architectural point: sending a large PDF into a prompt on every turn is expensive and non deterministic. Extract once, then generate from the structured result.

Four questions that settle it fast

  • Will anything downstream query, filter, or report on the result? Reports need fields, not paragraphs.
  • Does the same document type arrive again next week? A schema pays for itself when it does.
  • How many documents per run? One in a user flow suits a prompt template. Thousands needs batch.
  • Does a human read the output once and move on? Then structure is overhead.

In both cases, does the file have to be a ContentDocument?

No. Prompt Builder requires it. Document AI does not.

Prompt Builder needs the file to already exist as a Salesforce file before the prompt can see it. It comes in either as a File object passed as an input when invoking from Apex, an LWC, REST, or an agent action, or from the record's Notes and Attachments related list. Either way it is a ContentDocument and ContentVersion sitting in the org, counting against file storage.

Document AI does not require one. The real-time API takes the bytes inline in the request body, and batch mode works over files ingested by Data Cloud connectors that stay in the external store entirely.

POST /services/data/{api_version}/ssot/document-processing/actions/extract-data

{
  "mlModel": "llmgateway__VertexAIGemini20Flash001",
  "schemaConfig": "JSON_Schema",
  "files": [
    { "mimeType": "application/pdf", "Data": "<base64>" }
  ]
}

The response comes back as typed key and value pairs, one entry per field in the schema.

Why this matters in a design review. If documents already arrive in Salesforce through an Experience Cloud upload or email-to-case, both paths are open and you choose on the merits. If they arrive in S3, SharePoint, or an SFTP drop, forcing them into ContentDocument purely so a prompt template can read them is a storage bill you did not need to pay.

With Document AI, where does the uploaded file actually get stored?

Document AI is a processor, not a document repository. It never becomes the system of record for the file.

PathWhere the file ends upWhat persists
Real-time API Nowhere. The bytes travel as base64 in the request and are processed in memory Only the extracted JSON in the response, which you persist yourself
Batch over a UDLO Stays in the external blob store. Data Cloud references files rather than copying them, and the UDLO holds only metadata: file path, size, content type, parent relationships, timestamps Extracted data written into a new DLO based on your schema

Sample docs in the schema config UI Used to infer and validate the schema. Not a runtime path and not a document library The schema configuration itself. Confirm sample retention in your own org if PHI is involved

The consequence for regulated work: retention, records management, and audit stay attached to whichever store the document already lives in. Adopting Document AI does not pull documents into a new retention scope.

So Document AI only extracts the values and stores those, not the physical attachment in Data Cloud?

Yes on the file. Partly on the values, because where they land differs by mode.

On the file, that is correct. Data Cloud references unstructured files rather than copying them, so in batch mode the PDF stays in S3, Azure, GCS, Box, or wherever the connector points, and the UDLO row holds only metadata about it. In real-time mode the bytes are transient. If the file came from Salesforce it stays in ContentDocument, which is core Salesforce storage, not Data Cloud. No path puts the physical document into Data Cloud.

On the values, it depends on the mode. Batch mode persists them for you, into a new DLO shaped by your schema, which you then map to a DMO. Real-time mode persists nothing. It hands the extracted key and value pairs back in the API response, and you decide what happens next, whether that is a Flow writing onto a Case, Apex creating records, or an agent using them in the moment and never storing them at all.

One distinction to keep separate, and the one that gets asked about in a PHI conversation. All of the above is about the extraction path. If you also build a search index over that same UDMO for RAG grounding, Data Cloud chunks and vectorizes the content, and those chunks and embeddings do persist in Data Cloud. "Data Cloud does not copy the file" is accurate. It is not the same claim as "no representation of the content exists in Data Cloud."

And on the Prompt Builder side, does it read, extract, and store the attachment in ContentDocument?

The sequence runs the other way, and it reads rather than extracts.

The file has to already be a ContentDocument before the prompt can see it. Prompt Builder does not create or store it. Something else put it there: an Experience Cloud upload, email-to-case, a user dragging it onto a record, an API call. ContentDocument is a precondition on this path, not an output of it.

It reads, it does not extract. The model receives the PDF or image as multimodal input alongside your merge fields and returns text. There is no schema, no typed fields, no key and value pairs. If you ask for JSON in the instructions you may well get JSON, but nothing enforces it and you own the parsing and the failure handling.

Nothing is written back to the file. The ContentDocument is untouched by the run. Where the generated text lands depends on the template type: a Field Generation template writes into the target field on the record, a Sales Email template drops a draft in the composer, a Flex template returns text to whatever invoked it.

The clean contrast

Document AI reads bytes that may live anywhere, returns typed fields, and stores no file. Prompt Builder reads a file that must already be in Salesforce, returns prose, and stores no file either.

The cost argument worth making out loud. Because the file stays in ContentDocument and is re-sent to the model on every invocation, a prompt that reads a 40 page PDF pays the full token cost every time someone clicks the button. Document AI pays it once and the fields are reusable forever. That is the real reason extract-then-generate wins on recurring document types.

What else trips people up in a design review?

Five things that come up often enough to be worth having ready.

Naming. Data Cloud is now branded Data 360, so Document AI is documented under both names. Same feature, and someone will ask.

Model support is not universal. Prompt Builder file inputs only work on models that accept the file type, and the model limitations panel in the template config shows the real ceilings on file size and count. Check it there rather than trusting a blog, including this one.

Document AI is not the older tools. Intelligent Document Reader is OCR led and template oriented. MuleSoft IDP is a separate service with its own quotas and its own licensing. Neither is Document AI, and conflating them in front of a customer costs credibility.

Structured output from a prompt is a convention, not a guarantee. Ask a prompt template for JSON and you will usually get JSON, but nothing enforces it and you own the parsing and the failure handling. Document AI's schema is the enforced version of that promise.

Cost shape. A document inside a prompt burns tokens on every single call. An extraction runs once and the result is reusable forever. On a recurring document type that difference compounds fast.

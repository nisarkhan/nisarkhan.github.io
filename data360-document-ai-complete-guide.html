Data 360, Document AI, and the External Client App

Everything from one thread: how Data 360 relates to your org, why a Document AI build needs OAuth credentials to call that same org, and what each piece of the KYC tutorial is doing.

Naming note: Salesforce renamed Data Cloud to Data 360. Same product, both names appear in the docs.

Part 1

Where Data 360 actually lives

The starting point, because everything later follows from it.

One org, two engines

The instinct that Data 360 is a different instance is right. Data 360 runs within a dedicated functional domain hosted on Hyperforce, on AWS, and its storage is a native lakehouse built on Iceberg and Parquet with a Kubernetes-native compute fabric that runs Spark for processing and Hyper for SQL. Your org's records are not sitting in that lakehouse; copies of them are.

The nuance is that "altogether different" goes slightly too far. Metadata is designed, modeled, and stored as Salesforce metadata in a fully ACID-compliant database, and the Home Org is the org Data 360 is provisioned on. So the accurate split is:

Shared control plane

What exists, how it is modeled, and who can see it. Lives in the core home org.

Separate data plane

Where the rows are stored and processed. Lives in the Data 360 tenant on Hyperforce.

A hospital way to picture it

The core org is the front desk and chart system: one patient visit at a time, instantly and accurately. Data 360 is the records and analytics building across the street, holding every claim, lab result, and portal click from every system in bulk. Same ID badges, same directory of what is stored where, so staff walk between them without noticing. Different buildings, plumbing, and power.

A record's journey across the bridge

A service rep updates a patient's phone number. Watch which side each step happens on.

  1. The savecore

    Validation rules and triggers fire, and the change commits to the core database instantly.

  2. The copyData 360

    The CRM data stream writes the change into the Contact DLO as a new Iceberg snapshot. Minutes, not milliseconds.

  3. The mappingData 360

    Field mappings carry it into the Individual and Contact Point Phone DMOs.

  4. The matchData 360

    Identity resolution links this person to the same individual in the claims feed and the portal.

  5. The signalData 360

    A calculated insight counts missed appointments in 90 days. It crosses the threshold, so a Data Action fires.

  6. The actioncore

    A Flow creates a follow-up Task, the rep sees the unified profile, and an agent grounds its answer in the data graph.

The design consequence

Steps 1 and 6 are in core. Steps 2 to 5 are off-core. The round trip is a pipeline, not a transaction, so nothing on the right side can roll back the save on the left. Never put Data 360 in a save path.

Part 2

Why the build needs OAuth credentials

The part that feels wrong until you see where the request travels.

The External Client App is not a Document AI setting

Document AI doesn't need an External Client App. The REST API you call it through does.

Document AI runs in two modes. Batch processes documents referenced by an Unstructured Data Model Object, entirely inside the platform. Transactional processes one document via REST and returns structured JSON synchronously.

Choosing "Without a Source Object" when you built the schema put you on the transactional path. That path is only reachable as an HTTP endpoint, and every call to it must carry a bearer token. A token can only be issued to a registered app, which is what the ECA is.

What you're doingECA needed?Why
Building and testing a schema on the Document AI screenNoYou're logged in to the org UI. No API call from outside.
Batch processing documents behind a UDMONoRuns inside Data 360. Source connectors carry their own credentials.
Testing the extract API in PostmanYesPostman is an outside app.
An external portal or MuleSoft sending a documentYesClassic integration: client credentials or JWT bearer.
Your own Apex or Flow calling the extract APIYesAn HTTP callout to your own org is still an API call.

Same org, and you still need a key

This is the question that doesn't sit right at first: the Apex is in the core org, the endpoint is the core org, so what is the client ID and secret for?

The key has nothing to do with which org you're calling. It's about how.

Apex can reach Salesforce two ways

  • In-process: SOQL, DML, ConnectApi methods. The code never leaves the org's runtime, so it already runs as the current user and nobody asks who you are.
  • Over HTTP: Http.send(). The request leaves Apex, travels the network, and comes back in through yourdomain.my.salesforce.com, the same front door Postman uses. HTTP carries no memory of where a request came from, so the API layer sees an anonymous request and demands proof of identity.

You can prove it in Execute Anonymous. Same org, same code, rejected:

HttpRequest req = new HttpRequest();
req.setEndpoint(URL.getOrgDomainUrl().toExternalForm()
    + '/services/data/v65.0/ssot/document-processing/actions/extract-data');
req.setMethod('POST');
HttpResponse res = new Http().send(req);
// 401: INVALID_SESSION_ID, Session expired or invalid
Living in a house

Running SOQL is walking from the kitchen to the bedroom. Nobody checks. An HTTP callout is stepping outside and ringing your own doorbell. The door doesn't know it's you, so you need your key.

Why not reuse the logged-in user's session?

There isn't a reliable one to borrow. In a screen flow, UserInfo.getSessionId() returns a Lightning session, and Salesforce deliberately blocks those from making API calls. In async contexts like Queueable or scheduled jobs it can come back empty. Client credentials lets the platform mint a fresh token at any time, including a scheduled job at 2 a.m. with no human involved.

So what the credentials really are

A service account login for your own org's API. Client ID is the username, the secret is the password, the Run As user is who the token represents, and the Named Credential automates "log in, get a token, attach it" so your Apex never handles any of it. If Salesforce shipped Document AI as a native Apex method or standard Flow action, you'd need none of this, same as you don't need a token to run SOQL.

Which URL is actually called

Both calls go to your own org's My Domain URL, the one entered in the Named Credential. Using the org from the tutorial screenshots:

// Call 1: the Named Credential gets a token for you
POST https://orgfarm-7689eee47b-dev-ed.develop.my.salesforce.com/services/oauth2/token
     grant_type=client_credentials&client_id=3MVG9...&client_secret=****

// Call 2: the one your Apex writes
POST https://orgfarm-7689eee47b-dev-ed.develop.my.salesforce.com
     /services/data/v65.0/ssot/document-processing/actions/extract-data
     ?htmlEncode=false&extractDataWithConfidenceScore=true
Authorization: Bearer 00D...   (added by the Named Credential)

At runtime callout:DocumentAI_NamedCredential is simply replaced with that base URL.

What happens once it arrives

The URL is core. The work isn't. This is where Part 1 connects back:

  • The request comes back in through your org's API front door
  • Core validates the bearer token and the Run As user's permissions
  • The /ssot/ path is the Data 360 API family (ssot means "single source of truth"), so Salesforce routes it internally to your Data 360 tenant
  • Document AI loads the schema configuration, runs OCR, and sends the document to the LLM through the Einstein Trust Layer
  • The JSON returns the same way, into your Apex HttpResponse

Core is the reception desk. Data 360 is the lab behind it. You only ever talk to reception.

Worth knowing for other Data 360 APIs

The Query API and Ingestion API work differently: you trade your core token for a Data 360 token, then call a separate tenant host that typically ends in c360a.salesforce.com. Document AI's extract endpoint skips that step and handles the handoff internally, which is why the URL here stays on your core domain.

The two-user trap

In the tutorial you are the admin, the flow runner, and the Run As user all at once, which hides the fact that two different users are involved in every call.

The person running the flow

Needs the permission set with External Credential Principal Access. Otherwise the platform won't let their session use the stored key.

The ECA's Run As user

Whose permissions the Document AI call actually executes with, and whose name shows in API logs. Nobody logs in as this user.

How this bites

You roll the flow out to the KYC operations team. It works perfectly when you test it and fails for every rep, because the permission set was only assigned to you. Fix: assign it to the reps or their permission set group, and keep the Run As user a dedicated integration user.

What I noticed in DocumentAIExtractor.cls

Read from the course repo. It works for the demo, but a few things matter before real documents go through it.

It sends the whole file as base64Will hit limits

The class loads VersionData, base64-encodes it, and puts it in the JSON body. Base64 adds about a third to the size, and the blob, the encoded string, and the body all sit in heap at once. A screen flow is synchronous, so the 6 MB heap and callout size limits apply. Files around 1.5 to 2 MB can fail, well below Document AI's own 10 MB limit.

Salesforce's own resume sample sends a file reference instead:

// Now: the file bytes travel through Apex heap
'files' => new List<Object>{ new Map<String,Object>{ 'mimeType' => 'application/pdf', 'data' => base64Data } }

// Lighter: pass the ContentVersion Id
'files' => new List<Object>{ new Map<String,Object>{ 'fileId' => cv.Id } }

With fileId you can also drop VersionData from the SOQL query.

The MIME type is hardcoded to PDFBug

The class works out the right MIME type with getMimeType(), then ignores it and sends 'application/pdf'. A rep who photographs an ID card and uploads a JPG sends image bytes labeled as a PDF.

The config name must match exactlyGotcha

The body hardcodes 'idpConfigurationIdOrName' => 'KYC_Form'. If your published schema's API name differs, you get a 400. Better to pass it from the flow or custom metadata so one class serves several document types.

Dead code around the modelCleanup

It builds a requestBody map with mlModel set to Gemini 2.0 Flash, then sends a different map. The model actually used is whatever the schema configuration specifies.

The flow only processes the last fileBehavior

The loop overwrites ContentDocumentVar on every pass. If the upload allows multiple files, only the last is extracted. Restrict the upload to one file, or call the action per file.

It already asks for confidence scoresNice

The endpoint uses extractDataWithConfidenceScore=true and parseExtractedData() captures a score per field. Use it: flag any field below a threshold on the review screen so the rep checks it before the Contact updates.

It extracts government ID numbersGovernance

The mapping pulls PAN and Aadhaar numbers. Trust Layer PII masking doesn't currently apply to documents sent through Document AI, so these reach the model as-is. Store them in encrypted fields with tight field-level security, and confirm with the customer that sending ID documents to the chosen model meets their compliance rules.

Before a customer uses it

In order of how often it causes trouble:

Assign the permission set to the real users

Not just the admin who built it.

Swap the Run As user

A dedicated integration user with only the access Document AI needs, instead of System Administrator.

Trim the scopes

Keep api. Drop full and refresh_token, offline_access.

Send fileId, not base64

Removes the heap problem and the MIME bug in one change.

Plan for the API's pace

Synchronous, typically 5 to 15 seconds, capped at 50 calls per minute per tenant. Fine behind a button. Wrong in a bulk trigger.

The questions from the thread
Is Data 360 a different instance from the core platform? "Data cloud technically all together different instance than Platform instance. Data Cloud is a hyperscale platform"

Mostly yes, and the instinct is right. Data 360 runs in a dedicated functional domain on Hyperforce, on AWS, with a lakehouse built on Iceberg and Parquet and its own Spark and Hyper compute. Your org's rows are not in that lakehouse; copies of them are.

The one correction is that the control plane stays in core. Metadata is stored as Salesforce metadata in an ACID database, and the home org owns Setup, users, and permission sets. So: shared control plane, separate data plane.

Why do I need an External Client App just to create Document AI? "when i create a document AI in the data cloud why do i need to create external client app i do not understand that"

You don't, for Document AI itself. Building a schema on the Document AI screen needs nothing extra, and neither does the batch pipeline over a UDMO.

You need it because the tutorial uses the transactional pipeline, chosen the moment you picked "Without a Source Object". That pipeline is only reachable as a REST endpoint, every call needs a bearer token, and tokens are only issued to registered apps. The ECA is that registration.

The Apex is in the core org and the endpoint is the core org. What is the client ID and secret even for? "if your apex code still in the core org then what is the useage of client and secrete here?"

Why can't Apex reuse the logged-in user's session?

There's no reliable session to borrow. In a screen flow, UserInfo.getSessionId() returns a Lightning session, and Salesforce deliberately blocks those from making API calls. In async contexts like Queueable or scheduled jobs it can come back empty. Client credentials lets the platform mint a fresh token at any time, including an unattended job at 2 a.m.

What's the difference between the ECA, External Credential, Named Credential, and permission set?
  • External Client App: who is calling. The registered OAuth client.
  • External Credential: how to get a token, and where the key and secret live.
  • Permission set: who in the org may use that key.
  • Named Credential: where to send the call, plus it attaches the auth header.

Badge account, badge in the key cabinet, list of staff who may take it out, and the address on the order slip.

Why a callback URL if client credentials never redirects?

It does nothing for this flow. The field is required on the form, so tutorials fill it with a placeholder. Yours uses login.salesforce.com/services/oauth2/success; the Salesforce guide uses Postman's callback because it expects you to test there.

Which OAuth scopes does this actually need?

api is the one that matters. Salesforce's architect guidance lists api and cdp_ingest_api for the transactional pipeline. Your screenshot also selects full and refresh_token, offline_access; client credentials issues no refresh tokens, so that does nothing, and full is far more than the call needs.

Why isn't this calling a c360a.salesforce.com host?

Because the extract endpoint doesn't work that way. The Query API and Ingestion API make you trade your core token for a Data 360 token first, then call a separate tenant host that typically ends in c360a.salesforce.com. Document AI's extract endpoint lets you call the core domain and handles the handoff internally. Useful to know when the auth steps in Data 360 API docs suddenly look different.

Setup and operations
It works for me but fails for everyone else. Why?

Almost always the permission set. Two users are involved in every call and, as the builder, you're usually both, which hides the split.

  • The person running the flow needs External Credential Principal Access.
  • The ECA's Run As user is whose permissions the call executes with.

Assign the permission set to the real users or their permission set group, and make the Run As user a dedicated integration user.

Why does the call take so long?

The extraction API is fully synchronous, typically 5 to 15 seconds depending on file size and schema complexity. Set caller timeouts to at least 30 seconds. Fine behind a button a rep clicks; wrong anywhere that needs an instant response.

Can I run this from a record-triggered flow on a bulk load?

Not directly. The API allows 50 extraction calls per minute per tenant, and each call burns credits. A load of 500 documents would blow straight through it. For high volume, use the batch pipeline with a UDMO, which is what it's built for.

Does the extracted data end up in Data 360 or in my org?

In this tutorial, neither by default. The transactional pipeline returns JSON to the caller and persists nothing on its own. Your flow then writes selected fields onto the Contact, so those land in the core database.

If you want the extraction to feed identity resolution, calculated insights, or Agentforce grounding, route the payload into a DLO yourself, or use the batch pipeline, which writes to DLOs automatically.

Is the document's PII masked before it reaches the LLM?

No. The Einstein Trust Layer enforces zero data retention with the model provider, but masking operates at the prompt level, not the document level. Salesforce's architect guidance states masking isn't currently supported for multimodal input, so documents go to the model as-is.

Your tutorial extracts PAN and Aadhaar numbers, so raise this directly with any customer before real ID documents go through it.

Is "Extract Data from Document" in Flow the same thing?

No. That standard action belongs to the MuleSoft for Flow: IDP add-on and requires that license per user. It isn't the Data 360 Document AI REST path, so don't assume it removes the need for an ECA in a Data 360 design.
